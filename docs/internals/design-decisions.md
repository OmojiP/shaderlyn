## 判断できないときは報告しない

すべてのルールが従う原則です。

1. 知識が不完全なとき、「無いこと」を根拠にするルールは何も報告しない
2. 検査を見送ったときは、見送ったという事実を報告する（`SL0002` / `SL0003` / `SL0004`）
3. 解析の前提が揃っていないときは、見送らずにエラーにする（取り込みを 1 件も解決できなければ `TOOL0004`）

誤検出を出すルールは、ツール全体が信用されなくなる原因になります。
一方で、検査していないことを黙っていると「指摘が無い = 問題が無い」と受け取られ、誤検出よりも発見が遅れます。

規則は推測で書かず、fxc / DXC / Unity の出力と突き合わせて決めます。

## 配布と拡張

- **CLI は Native AOT の単一バイナリで配る。** GitHub Actions で PR ごとに起動する用途では、ランタイム不要と速い起動の価値が大きい。
  全プロジェクトで `IsAotCompatible` と `TreatWarningsAsErrors` を有効にし、リフレクションを使うとビルドが通らないようにしている
- **組み込みのルールは `BuiltInAnalyzers.All` に静的に並べる。** AOT ではアセンブリを走査して集められない。登録漏れはテストがリフレクションで見つける
- **自作ルールは C# で書き、自分の CLI としてビルドする。** AOT ではプラグイン DLL を動的に読み込めない。
  設定ファイルにルールを書く経路は持たない。書ける形を足すたびに書式・読み取り・ドキュメントが増え、やがて YAML の上に貧弱な言語を作ることになる
- **YAML の読み取りは必要な範囲だけ自前で書く。** 一般的なライブラリはリフレクションを使い、知らないキーも報告しない。
  自前なら、打ち間違えたキー・タブの字下げ・重複したキーを報告できる。アンカー、複数ドキュメント、複数行スカラーは扱わない
- **言語サーバーの JSON-RPC も自前で書く。** YAML と同じ理由で、依存を増やさない

## 構文木

- **red/green ツリーは採らない。** ノードが範囲と親を直接持つ 1 層の木にする。
  red/green の利点（差分の再構築とノードの共有）は、遅いのがマクロ展開で、シェーダーが数千行に収まるこのツールでは効かない。
  親が 1 つに決まっていることを前提にしたコードが多い（`ConditionMap`、`LocalScopes`、ホバーなど）
- **ShaderLab の命令の引数は、行末と既知の命令名で区切る。** 引数の個数表は持たない。
  表に無い新しい命令を構文エラーにすると、正しいシェーダーを壊れていると言うことになる。
  `Pass { Cull Off ZWrite Off }` のように 1 行に詰めた形のために、命令名の一覧（`ShaderLabParser.CommandNames`）だけを切れ目に使う。
  ほかの命令の引数値として現れる名前を、この一覧に入れてはならない

## HLSL の解析単位

- **HLSL はマクロ展開と `#include` の解決を済ませたトークン列から木を作る。** マクロを展開しなければ構文として成立しない（`TEXTURE2D(_BaseMap);`）。
  元のテキストは復元できないので、診断の位置は `HlslSyntaxNode.GetLocation()` で求める
- **環境の条件（`SHADER_API_*`、`UNITY_VERSION`）は 1 通りだけ解く。** ビルドで決まる値で、書き手が選ぶ軸ではない。両方を展開しても直せる誤りはほとんど増えない
- **埋め込み HLSL は切り出さず、元のファイルと同じ長さで解析範囲の外を空白にしたテキストで解析する。**
  位置の変換が要らず、`HLSLINCLUDE` の差し込みもファイル上の順序のまま再現される。`HLSLPROGRAM` 1 つが 1 つの解析単位になる
- **ブロックごとに Unity が足すものを再現する。** `#pragma target` からの `SHADER_TARGET`、`CGPROGRAM` が暗黙に取り込むヘッダ、
  サーフェスシェーダーが取り込むヘッダ。自動で取り込むヘッダは、すべて見つかったときだけ足す
- **HLSL 単体のファイル（`.compute` / `.hlsl` など）はファイル全体を 1 つの `HLSLPROGRAM` として扱う。**
  ShaderLab の木は全部を空白にしたテキストから作るので、埋め込み HLSL と同じ道を通る。単体ファイル用の道を別に作ると、その道だけ検査が抜ける
- **`.hlsl` / `.cginc` / `.hlslinc` はフォルダーの探索では拾わない。** プロジェクトの下には Unity のヘッダもある。直接指定したときだけ解析する
- **`.compute` はカーネルごとに 1 つの解析単位にする。** `#pragma kernel K NAME=VALUE` の定義はそのカーネルだけに効く。
  解析単位はどれも同じ位置から始まるので、宣言を集めるルールは位置とカーネル名の組（`AnalyzedProgram.BlockKey`）で分ける

## 条件付きコンパイル

詳細は [条件付きコンパイルの扱い](../guide/conditional-compilation.md) にあります。判断の要点だけを挙げます。

- **全組み合わせは作らない。** URP の `Lit.shader` は 42 個のキーワードを宣言しており、組み合わせは 2 の 42 乗になる
- **キーワードの `#if` の両方の分岐を 1 本の木に並べ、ノードごとに出現条件を付ける。**
  構成ごとの木に分けると、同じヘッダを構成の数だけ展開するうえ、構成をまたいだ判断（呼ぶ条件と定義がある条件の食い違いなど）ができない
- **並べられない領域だけ、キーワードを有効にした構成を別に展開して突き合わせる。** 条件が見ていないキーワードは、有効にしてもコードが変わらないので展開しない
- **判定できないものは並べない側へ倒す。** 誤って並べると構文木が壊れ、その先の判断がすべて狂う
- **表しきれない条件は `Unknown` にする。** 近い条件で代用すると、「この構成では存在しない」という誤った判断を生む
- **展開する構成には上限を置く（既定 8）。** 誤検出より解析時間を取るが、時間は `--max-symbol-variants` で戻せる。上限で落とした分は `SL0003` で伝える
- **互いに関係しないキーワードは 1 回の展開にまとめる。** 1 つずつ展開したときと結果が変わらないことを、展開の後に確かめる。
  確かめられなければ 1 つずつ展開し直す
- **`_` の無い `shader_feature` の行は、「どれも無い」構成もあるものとして扱う。** Unity の説明ではっきりしないので、実在する側へ倒している
- **`multi_compile_fog` などの組み込みの宣言が作るシンボルは、Unity のマニュアルの一覧から表にしている**（`ShaderSymbols.BuiltInSets`）

## 型と名前

- **型を判定できないときは「分からない」を返す。** 推測で型を返すと、正しいシェーダーを誤りとして指摘する。ルールは「分からない」を受け取ったら報告しない
- **型は構文木から求める。** トークン列の上で式の形から型を読むのは、パーサーの劣化した複製にしかならない
- **「分からない」の 2 種類を区別する。** `real` / `fixed` / `min16float` のように規則が決まらないもの（設計上の限界）と、
  組み込み関数の表に載せていないもの（未実装）は、混ぜて「扱わない」とまとめない
- **オーバーロードは、選ばずに済むなら選ばない。** 呼び出しの誤りは、実引数を受け付ける候補が 1 つも無いときだけ報告する
- **関数の中の名前は、使っている位置から波括弧ごとに外側へたどって解決する**（`LocalScopes`、`ExpressionTypeBinder.ResolveName`）。
  分岐ごとに型の違う一時変数を宣言するのは普通の書き方で、関数全体で 1 つの表に集めると型の検査が止まる。
  前後は文字位置ではなく文の順番で比べる。マクロが宣言と使用の両方を生むと、位置では前後が決まらない
- **`for` の初期化の変数は、fxc と同じく囲む波括弧の範囲へ漏らす。** DXC の `-HV 2021` は閉じ込めるが、Unity で通るコードを基準にする
- **名前の解決は 1 か所で行う。** ルールごとに引き方が違うと、同じ名前を片方は局所変数、片方はグローバル変数と読むことになる

## 利用者が書いたヘッダ

`#include` で取り込んだファイルのうち、Unity と外部パッケージのヘッダ以外は利用者のファイルとして指摘の対象にします。

- **「直せないもの」を判定する。** 直せないヘッダの置き場所はプロジェクトの `Library` と Unity Editor の同梱物に限られる。
  「直せるもの」を列挙すると、`file:` で参照するローカルのパッケージのような置き場所を取りこぼす
- **ヘッダは取り込む側の文脈で解析する。** 単体で解析すると、取り込む側が先に宣言した名前を「宣言されていない」と誤って報告し、どの構成が実在するかも分からない
- **同じヘッダの同じ指摘は、取り込むシェーダーが複数あっても 1 件にまとめる**
- **シェーダー単位の宣言に関わる検査（HL0330 / HL0331 / SL0003 / SL0004）はヘッダを対象にしない。**
  1 つのシェーダーの宣言を根拠にヘッダを指摘すると、別のシェーダーにとっては誤りになる

以前は取り込んだヘッダをすべて報告の対象から外していました。念頭にあったのが `UnityCG.cginc` のような直せないヘッダだけで、
利用者が書いた共通のヘッダは検討されていませんでした。テストの取り込みも Unity のヘッダを模したものばかりでした。
「ヘッダ = 直せないもの」のような前提を置くときは、それが崩れる例をテストに入れてください。

## 速さ

- **直す前に測る。** `--timings` で段ごとの CPU 時間を見て、測って効いたものだけを入れる。どの変更も、指摘が変わらないことを確かめてから入れる
- **測るときは CLI を直接実行する。** `dotnet test` 経由では並列度が変わる。同じ入力を 2 回走らせて結果を比べる（キャッシュの欠陥は非決定の形で出る）
- **Unity や外部パッケージのヘッダの関数の中身は構文木にしない。** ルールがそこに求めるのは関数の形と宣言だけで、報告できる場所も無い
- **取り込みの展開結果は、その展開が読んだ名前の状態で照合して使い回す。** 読んだ名前は表の型が必ず知らせる。読む箇所ごとに記録を足す形にすると、足し忘れた箇所で違う状態の結果を使い回す
- **実行をまたぐキャッシュ（`--cache`）は、取り込むファイル一式の内容を鍵に含める。** 設定ファイルは項目ごとに拾わず中身をそのまま混ぜる。項目ごとに拾うと、書式が増えたときに拾い忘れる
- **CLI と言語サーバーはサーバー GC を使う。** 割り当てが多く、ワークステーション GC では回収が律速になる

## エディタ

- **解析を 2 段に分ける。** 編集のたびには ShaderLab だけの検査（数 ms）、開いたときと保存したときに意味解析（Pass の数に比例して数百 ms）を走らせる
- **第 1 段の結果を出すとき、前回の意味解析の結果は捨てる。** 編集で位置がずれた指摘は、指摘が消えるより悪い
- **キーワードの構成は、利用者が選んだときだけ表示に使う。** 既定は「どの構成でも外れる範囲」だけを薄くする。
  最初から構成を選ぶと、出荷されるコードが意味の無いものに見える。選べるのは実在する構成だけにする（同じ行は 1 つ、`_` の無い行は空にできない）
- **表示のために選んだ構成は、指摘には使わない。** 足すと、ありえない組み合わせを検査することになる

## やらないと決めたこと

| 案 | やらない理由 |
| --- | --- |
| プラグイン DLL を読み込む | Native AOT では読み込めない |
| 設定ファイルにルールを書く | 書ける形ごとに書式とドキュメントが増え、述語を書きたい要望に応えられない。データをルールへ渡すなら C# のルールの中で読む |
| ShaderLab の命令ごとの引数の個数表 | 表に無い新しい命令を構文エラーにしてしまう |
| 宣言されたキーワードを全部 1 つずつ展開する | 条件が見ていないキーワードは結果を変えない。`Lit.shader` だけで 42 回の展開になる |
| 既定の構成と同じトークン列になるバリアントを捨てる | 同じかを知るにはプリプロセスまで走らせる必要があり、省けるのは構文解析の一部だけ |
| 違いの位置が分かれていなくても、キーワードをまとめて展開する | あるキーワードだけのときに壊れるコードを、ほかのキーワードが隠す |
| 子の一覧をノードに持たせる | 作って測ったら遅くなった |
| `--changed-only`（git の差分にあるファイルだけを解析） | ヘッダを直した PR で、影響を受けるシェーダーを見逃す。`--cache` が見逃しの無い形で同じ効果を出す |
| マクロ定義のハッシュを覚える | 作って測ったが、差はばらつきの幅の中だった |
| 編集が触れた Pass だけを解析し直す | 再利用した結果の位置は編集前のテキストを指しており、位置のずれた指摘を作り込みやすい |

## 残っている課題

原則（[判断できないときは報告しない](#判断できないときは報告しない)の 2）に反して、見送ったことを伝えていないものがあります。

- 式の型が分からず、型を使う検査を見送った箇所（Unity 同梱の `.shader` 209 本で 57 か所）
- 構成ごとに型を決める仮定が 16 を超えて判断しなかった箇所
- 条件に書かれていない組み合わせ（別々の `#ifdef _A` と `#ifdef _B` が同時に有効な構成）
- `HLSLINCLUDE` しか持たないシェーダー（解析単位が 1 つも無い）

ほかに、まだ手を付けていないものです。

- 利用者のヘッダの中の、中身の違うマクロの再定義は報告しない（条件付きの定義の追跡が、解析しているファイルだけを対象にしている）
- VS Code でヘッダを単体で開いたときは、取り込む側の文脈が無い
- 同じヘッダの宣言のノードを Pass の数だけ作っている。共有するとノードの親が 1 つに決まらなくなる
