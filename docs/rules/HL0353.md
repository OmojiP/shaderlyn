# HL0353: 構成によっては成分が切り捨てられます

分類: Correctness / 既定の重要度: 警告

## 何を検出するか

同じ名前を条件ごとに違う型で宣言していて、
一部の構成でだけ成分の落ちる変換になっている状態です。

```hlsl
float ReturnFloat()
{
    #pragma multi_compile _A _B

    #if defined(_A)
    float a = 1.0;
    #elif defined(_B)
    float3 a = float3(1.0, 2.0, 3.0);
    #endif

    return a;   // !_A && _B のとき float3 を float へ渡している
}
```

`_A` の構成では何も起きません。`_B` の構成でだけ `y` と `z` が黙って落ちます。

代入・初期化・`return` の 3 か所を見ます。

## なぜ問題か

**コンパイルは成功します。** HLSL は成分を減らす変換を警告 (fxc の X3206) 付きで通します。

問題は、書いた本人が両方の構成を意識しているのに、
片方の構成でだけ値が落ちる形になっていることです。
`_A` で動かして確かめたコードが `_B` では違う結果を出すため、
特定のシンボルを有効にしたときだけ現れる不具合になります。

## どう直すか

落とすつもりなら、どの成分を使うのかを書いてください。

```hlsl
#if defined(_A)
return a;
#else
return a.x;
#endif
```

どの構成でも同じ型にできるなら、そのほうが読みやすくなります。

```hlsl
#if defined(_A)
float3 a = float3(1.0, 1.0, 1.0);
#elif defined(_B)
float3 a = float3(1.0, 2.0, 3.0);
#endif
```

## 誤検出だと思ったら

このルールは次の場合に発火しません。

- 条件によらず型が決まる場合。
  `float Narrow(float3 v) { return v; }` のような切り捨ては報告しません。
  意図して書く場面が多く、どこでも報告すると読まれなくなります
- 渡せない変換の場合。成分が増える向きは [HL0350](HL0350.md) /
  [HL0351](HL0351.md) の領分です
- スカラーを渡している場合。全成分へ複製されるので値は落ちません
- 構成を決めても型が分からない場合
- 調べる構成が多すぎる場合。1 つの式につき 16 通りまでを見ます
- **構成を固定して解析した場合。**
  固定すると、その構成の宣言しか残りません。
  上の例を `_B` に固定すると `float3 a` だけが残り、
  条件によらない切り捨てと区別が付かなくなります。
  「型を書き分けた」という事実そのものが消えるため、
  このルールは構成をまたいで見たときにだけ報告します
