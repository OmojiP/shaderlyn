# GL0003: GLSL のプリプロセッサの指令の誤りです

分類: Correctness / 既定の重要度: エラー

## 何を検出するか

GLSL のファイルで、glslang が誤りにするプリプロセッサの指令の書き方です。

今は次のものを検査します (glslang 16.6.0 のプリプロセッサと同じ)。

- ES (`#version 100`、`#version 300 es` など) で、`#if` / `#elif` の式に定義されていないマクロを書いたもの

```glsl
#version 300 es
precision mediump float;
out vec4 o;

#if USE_FOG          // USE_FOG はどこでも定義されていない
#endif

void main() { o = vec4(1.0); }
```

`&&` の左が 0 のときと、`||` の左が 0 でないときの右の項は評価しないので、報告しません。
`#if defined(USE_FOG) && USE_FOG` は書けます。

- `#extension` の形の誤り。`#extension 名前 : 振る舞い` の順に書き、振る舞いは `require`・`enable`・`warn`・`disable` のどれかです。
  後ろには何も書けません。`all` には `require` と `enable` を書けません

```glsl
#extension GL_EXT_ray_query : on   // on は振る舞いではない
#extension all : enable            // all には warn か disable だけを書ける
```

- 予約された名前の `#define` / `#undef`。`GL_` で始まる名前と `defined` はどのバージョンでも、`__` を含む名前は ES の 3.00 より前で、
  `__LINE__`・`__FILE__`・`__VERSION__` は ES の 3.00 からも書けません (`GL_EXT_spirv_intrinsics` を有効にすれば `GL_` と `__` の名前は書けます)
- `#pragma optimize` / `#pragma debug` の形 (`#pragma optimize(on)` の形でないもの) と、SPIR-V を作るときの `#pragma STDGL` の形 (`#pragma STDGL invariant(all)` でないもの)
- ファイルの最初 (前にはコメントと空白だけ) でない `#version` と、2 つ目の `#version`。ES の 3.00 からは、前にコメントや空の行も書けません
- 1024 文字を越える名前と数のリテラル (glslang のトークンの長さの上限)
- 到達した `#error`。読み飛ばす分岐の中のものは報告しません

```glsl
#ifndef MAX_LIGHTS
#error MAX_LIGHTS を定義してください   // MAX_LIGHTS が定義されていなければ到達する
#endif
```

`#if` の式は glslang と同じく `int` (32 ビット) で計算します。評価できない式 (閉じていない括弧など) の `#if` は、glslang と同じく通る分岐として読みます。

## なぜ問題か

C と、ES でない GLSL では、`#if` の式の定義されていない名前は 0 として読みます。
ES ではそれが誤りで、glslang (Vulkan の SDK の `glslangValidator` と `glslc`) がコンパイルを止めます。

## どう直すか

マクロを定義するか、`defined(…)` で定義されているかを先に確かめてください。

```glsl
#if defined(USE_FOG) && USE_FOG
#endif
```

`#extension` は `#extension GL_EXT_ray_query : enable` の形で書いてください。

`#error` は、到達しないようにマクロを定義するか、条件を直してください。

## 誤検出だと思ったら

コンパイラに渡すマクロ (glslang の `-D` など) は、`--define 名前=値` (設定ファイルは `defines`) で渡してください。渡さないと、定義されていないマクロとして読みます。`#error` に到達するのも、多くはこのためです。
