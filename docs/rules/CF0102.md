# CF0102: 未解析のシンボル構成が存在します

分類: Usage / 既定の重要度: 情報 / 0.3.1 より前の ID: HL0006

## 何を検出するか

`#pragma shader_feature` / `#pragma multi_compile` で宣言されたシンボルのうち、
解析が展開しきれなかったものがあるファイルです。

展開しなかったシンボルごとに 1 件報告します。報告位置は、そのシンボルを参照する**最初の条件**
（`#ifdef _NORMALMAP` など）です。同じシンボルを参照する条件がほかにもあれば、その分岐の中も解析していません。

```
Lit.shader(16:20): info CF0102: シンボル '_NORMALMAP' を有効にした構成は未解析です。
 16 |             #ifdef _NORMALMAP
```

条件がヘッダの中にしか無いシンボル（`.shader` で宣言して、共通の `.hlsl` の機能だけを切り替えるものなど）は、
このファイルでそのシンボルを宣言した `#pragma` の行に出ます。
`#pragma multi_compile_instancing` のように名前を書かない組み込みの宣言が作るシンボル (`INSTANCING_ON` など) は、その宣言の行に出ます。
宣言も条件もこのファイルにない場合は、ファイルの先頭に報告します。

入れ子や論理積の条件でしか通らない分岐のために、シンボルの組を同時に有効にした構成も展開します。
その構成を展開しなかった場合は、組ごとに 1 件出ます。位置は、その組でしか通らない分岐を始めた指令です。
その指令が取り込んだヘッダの中にある場合は、指摘をヘッダには出せないので、ファイルの先頭に出ます。

```
Lit.shader(24:14): info CF0102: シンボル '_A' と '_B' を同時に有効にした構成は未解析です。
 24 |             #ifdef _B
```

組の中のシンボルは、1 つずつなら調べていることがあります。
その場合、`_A` だけ・`_B` だけで通る分岐は読んでいます。読んでいないのは、両方が有効なときだけ通る分岐です。

## なぜ問題か

シンボルの分岐は「無効な分岐」ではありません。

```hlsl
#pragma shader_feature_local _NORMALMAP

#ifdef _NORMALMAP
    TEXTURE2D(_BumpMap);
    SAMPLER(sampler_BumpMap);
#endif
```

`_NORMALMAP` はマテリアルの `EnableKeyword` からも、C# の
`Material.EnableKeyword("_NORMALMAP")` からも切り替えられます。
つまり宣言されたシンボルの経路はどれもいつか通るコードであり、
既定の構成だけを読んで済ませると、次のようなものが見えません。

- その分岐の中にしかない構文エラー
- その分岐の中でしか使われていないプロパティ
  (無効な構成だけを見て [SL1001](SL1001.md) / [SL1004](SL1004.md) を報告すると誤検出になります)

そのため解析では、シェーダー内の条件に書かれたシンボルを
1 つずつ有効にした構成も追加で展開します。
Unity に同梱されているシェーダー 209 件を調べると、この展開によって
SL1001 の指摘は 352 件から 92 件へ、SL1004 は 135 件から 14 件へ減りました。
減った分はすべて、シンボルの中でだけ使われていたプロパティです。

ただし、構成を展開するには処理時間がかかります。
組み合わせをすべて試すのは現実的ではありません
(URP の `Lit.shader` は 1 ファイルで 42 個のシンボルを宣言しています)。
1 つずつの展開にも上限を置いています (既定 8)。

上限に達したことを伝えないままでいると、調べていない箇所が「問題なし」と受け取られます。
この指摘はその事実を伝えるためのものです。

互いに関係しないシンボルは、1 回の展開にまとめて有効にします（最大 8 個）。
まとめた分は上限を 1 回分しか使いません。まとめるのは、有効にして変わる場所が別々の関数・構造体などにあり、
互いの宣言を使わないシンボルだけです。分岐の中でマクロを定義してコードで使うシンボルや、
分岐の中でヘッダを取り込むシンボルもまとめず、1 つずつ展開します。

上限に達したときに落とす順序は決まっています。

1. 互いに関係しないシンボルのまとめ
2. このファイルに書かれた条件が見ているシンボル（1 つずつの構成）
3. 条件に書かれた組（論理積・入れ子）
4. 取り込んだヘッダ自身が宣言したシンボルの条件から作った構成

上限に達した場合は、リストの下から順に省きます。そのため、互いに関係しないシンボルの組み合わせと、このファイルの条件から作る構成は最後まで残ります。

## どう直すか

上限を上げると、その分の経路も調べられます。

```
shaderlyn Assets/Shaders --unity-project . --max-symbol-variants 16
```

解析時間はシンボルの数に比例して伸びます。
Unity 同梱の 209 件では、既定の 8 で 29 秒から 63 秒になりました
(ファイルを 1 件ずつ解析した場合。CLI はファイルを並列に処理するのでさらに短くなります)。
CI で時間が問題になる場合は、上限を下げてこの指摘を受け入れる判断もあります。

どのシンボルが構成ごとの展開になったか、その原因の `#if` はどこかは、`--inspect` の「シンボルの扱い」タブで確認できます。
構成ごとの展開になるコードの形は
[解析方法が分かれる例](../guide/conditional-compilation.md#解析方法が分かれる例) にまとめています。

## 誤検出だと思ったら

この指摘は「解析がどこまで調べたか」の報告であり、
シェーダーの誤りを指すものではありません。
指摘の数を減らすためではなく、
調べていない範囲を承知したうえで無効化してください。
