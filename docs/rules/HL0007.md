# HL0007: 構成によって文の形が変わる箇所があります

分類: Usage / 既定の重要度: 情報

## 何を検出するか

同じ場所が構成によって**別の種類の文**になるため、
その箇所の出現条件が分からなかった状態です。

```hlsl
#pragma multi_compile _ _MODE_A _MODE_B _MODE_C _MODE_D

#if defined(_MODE_A)
#define BODY { v = 1; }
#elif defined(_MODE_B)
#define BODY v = 2;
#elif defined(_MODE_C)
#define BODY v = 3;
#elif defined(_MODE_D)
#define BODY v = 4;
#else
#define BODY v = 5;
#endif

if (v > 0)
    BODY
```

`if` の本体が、一方ではブロック、もう一方では式文になります。
定義が 5 通りあるので、使う文を定義ごとに複製することもできません
（[条件で中身が変わるマクロ](../guide/conditional-compilation.md#33-条件で中身が変わるマクロ条件の巻き上げ)）。
構成ごとに組み立てた構文木を比べても、
この位置に対応するノードが見つかりません。

`#elif`・入れ子の `#if`・`#undef`・別々の `#ifdef` での書き分けや、分岐に `#define` 以外のコードもある形、
1 つの文で中身の変わるマクロを 2 つ・3 つ使う形は、文を複製して扱えるため、この指摘は出ません。
利用者が書いて取り込んだヘッダで書き分けた場合も同じです。複製で扱えないのは、主に次の形です。

| 形 | 例 |
| --- | --- |
| 定義が 5 通り以上になる（どの定義も当てはまらない構成の分を含む） | 上の例 |
| 1 つの文で中身の変わるマクロを 4 つ以上使う、または定義の組み合わせが 9 通り以上になる | 3 通りのマクロ 2 つと 2 通りのマクロ 1 つ (12 通り) を 1 つの文で使う |
| 定義を書き分けた分岐にコードがあり、`#undef` か `#include` もある | `#elif` の分岐で、`#undef` してマクロを定義し直し、同じ分岐に関数もある |

利用者が書いたヘッダの中のマクロでこの形になった場合は、ヘッダのマクロの本体の位置に出ます。
Unity や外部パッケージのヘッダの中では出しません（利用者に直しようがないため）。

## 何は検出しないか

**`#if` が構文の単位をまたいでいること自体は、この規則の対象ではありません。**

```hlsl
#ifdef SHADER_DEBUG
half4 frag(Varyings IN) : SV_Target
{
    return IN.debugColor;
#else
half4 frag(Varyings IN) : SV_Target
{
    return 0;
#endif
}
```

この形は 1 本のトークン列に連結すると構文が成立しませんが、
構成ごとに組み立てて突き合わせる経路へ回り、そこで対応が取れます。
どちらの分岐の中も検査されます。

**同じ文の中身が構成によって入れ替わるだけの形も、対象ではありません。**

```hlsl
#ifndef USE_SECOND_CLOUD_LAYER
    #define LAYER       0
#else
    #define LAYER       dispatchThreadId.z
#endif

uv.x -= _Rotation(LAYER);
```

`LAYER` はリテラルにもメンバー参照にもなりますが、
この文は構成ごとの形を**両方とも残して**あります。
今の形では、使う文を定義ごとに複製して 1 本の木に並べます。
別のマクロを通して使うなど、文を複製できない場合も、解析器は両方を選択肢として残します。

## なぜ追えないのか

この解析器は、構成ごとに構文木を組み立ててから突き合わせます。
対応付けの鍵は「ノードの種類」と「元のソースでの位置」です。

同じ位置に違う種類のノードが立ったときは、対応を取る代わりに、
**両方をその構成でだけ立つ選択肢として残します**。
既定の構成の側にはシンボルの否定を、バリアントの側にはシンボルを付け、
ルールは両方を歩いてそれぞれの条件で判断します。
SuperC (Gazzillo &amp; Grimm, PLDI 2012) が条件付きの選択肢 (static choice) を
構文木に残すのと同じ考え方です。
SuperC は構文解析そのものを条件で分岐させ（fork）、同じ状態へ戻ったところで併合します（merge）。
この解析器は、構文解析には手を入れず、文・宣言の単位で同じことを行います。

残るのは、**分ける単位が見つからない**場合です。
分けてよいのは文と宣言で、しかもその単位自身のトークンが構成で変わっているときだけです。
上の `if` の例では、変わっているのは本体の文の種類で、
`if` 文自身のトークン (`if ( v > 0 )`) は構成によらず同じです。
`if` 文ごと分けてしまうと、どの構成にもあるコードまで条件付きになってしまうため、そうはしません。

## なぜ問題か

この箇所では、条件を根拠にするルールが何も報告しません。

[HL0311](HL0311.md) / [HL0313](HL0313.md) / [HL0340](HL0340.md) は、
「使う条件」と「ある条件」を突き合わせて判断します。
条件が分からない箇所では、どちらも成り立たないため何も言えません。

報告しないのは正しい振る舞いです。
分からないものを根拠に指摘を出せば、正しいコードを誤りとして指摘することになります。

しかし、報告を見送ったことを、伝えないままにしてはいけません。
利用者から見ると「問題が無かった」のと区別が付きません。

## どう直すか

やり方は 3 つあります。どれでも条件が追えるようになります。
方法 1 なら、構成ごとにコードを展開する必要はありません。

**1. 分岐を文の側へ移す。** マクロではなく、使う場所を条件で分けます。

```hlsl
if (v > 0)
{
#if defined(_MODE_A)
    v = 1;
#elif defined(_MODE_B)
    v = 2;
#else
    v = 3;
#endif
}
```

**2. 定義の種類をそろえる。** 中身が変わっても、文の種類が同じなら対応が取れます。

```hlsl
#if defined(_MODE_A)
#define BODY v = 1;
#elif defined(_MODE_B)
#define BODY v = 2;
// … (_MODE_C / _MODE_D も v = 3; / v = 4;)
#else
#define BODY v = 5;
#endif
```

**3. 書き分けを複製できる形にする。** 定義を 4 通り以内に減らすか、
分岐にコードと `#undef` や入れ子の `#if` を一緒に書かないようにすると、
使う文を定義ごとに複製して 1 本の木に並べられます。マクロの中身はそのままでかまいません。

## どれくらい起きるか

Unity 同梱のシェーダー 401 件（Unity 6000.0.60f1）では 0 件でした。
`BakeCloudTexture.compute` と `OpaqueAtmosphericScattering.shader` の 2 件は、
選択肢として残すようにしたことで報告されなくなっています。
